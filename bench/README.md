# 唯一约束维护方向评测台（不改内核）

本目录是 `internal/` 之外的独立评测代码，用于评估 LaminaDB 在大关系上持续维护
唯一约束的成本。它**不修改任何内核文件**（`git diff -- internal/ cmd/` 为空），
也不被生产二进制引用。

## 三个被比较的维护方向

- **方向 A — 基线（当前内核实现）**：每次提交 `versions.Store.Scan` 全关系取可见行，
  `overlay` 写集，再对全量可见行重建一个临时 `map[token]key` 做唯一判定。
  对应 `internal/engine/constraints.go` 的 `unique`/`checkUnique`。重启时
  `Open` 对每个关系再跑一遍同样的全表校验（`database.go`）。
- **方向 B — 常驻“当前态” owner 映射**：维护 `map[唯一值token] -> 持有主键`，
  只含**当前可见**的非空值（多个 null 不入表）。提交时只读取写集相关键和这些键
  目标值的当前持有者，按“提交后最终状态”判定；成功后增量推进映射。
- **方向 C — 复用现有历史候选树点查**：沿用 `index.Tree` 的历史 `(value,key)` 候选，
  对写集目标值做等值点查，再回版本链判活并叠加写集。树保留全部历史候选。

三者对“同事务置换 / 释放后复用 / 删除后复用 / 真冲突 / 多个 null”的判定必须一致；
模拟器内置 `correctness` 用例强制这一点，不一致即非零退出。

## 复跑方式

需要 Go 1.25（仓库 Dockerfile 同版本）。评测代码与生产模块隔离。

```sh
# 1) 算法模拟器（同构内存结构，量新增状态/校验工作/恢复重建，不做 fsync）
go run -C bench/sim . -scale correctness   # 语义一致性闸门
go run -C bench/sim . -scale standard      # N=1万，6 个负载
go run -C bench/sim . -scale large         # N=10万，4 个负载（A 较慢，分钟级）

# 2) 端到端（真实 laminad 进程 + HTTP + 每提交 fsync）
go build -o /tmp/laminad-baseline ./cmd/laminad
python3 -I bench/e2e/drive.py --binary /tmp/laminad-baseline \
        --sizes 1000,8000,30000 --small-commits 150
```

## 指标口径

- `rows_scanned`：方向 A 每次提交进入唯一校验的可见行数总和（∑ N，随提交数×关系规模）。
- `lookups`：方向 B 每次提交触碰的目标值 owner 查询次数（∝ 写集大小，与 N 无关）。
- `cand_rows`：方向 C 等值点查遍历的**历史候选**行数（随历史版本累积膨胀）。
- `hist_entries`：历史候选树条目数；`heap_B`：该方向结构的常驻堆占用（GC 后采样）。
- `rebuild`：方向 B 重启时从最终 store 全量重建 owner 映射的耗时与条目数。
- 端到端 `reopen_ms` 是**整个进程重启**（WAL 恢复 + 每关系全表唯一校验 + 索引重建），
  其中唯一校验是全表 O(N) 项之一，不是唯一成本。

## 原始结果（本机，Go 1.25 linux/amd64，数值随机器浮动，趋势稳定）

### 模拟器 N=10000，2000 个小提交（batch=2）

| 方向 | 耗时 | 校验工作量 | 额外常驻堆 | 恢复重建 |
| --- | --- | --- | --- | --- |
| A | ~7.9 s | 扫描 2.0e7 行（2000×10000） | 0（临时 map 用完即弃） | 每次重启全表 |
| B | ~2 ms | 4000 次 owner 查询 | ~+2.5 MB | 1.4 ms / 1万条 |
| C | ~44–67 ms | 历史候选 36–4768 行/负载 | ~+5.3 MB | 同 index.Build 全量 |

### 模拟器 N=100000，4000 个小提交

| 方向 | 耗时 | 校验工作量 | 额外常驻堆 | 恢复重建 |
| --- | --- | --- | --- | --- |
| A | ~2m18s | 扫描 4.0e8 行 | 0 | 每次重启全表 |
| B | ~6–8 ms | 8000 次查询 | ~+20 MB | ~19 ms / 10万条 |
| C | 0.68–1.23 s | swap 下历史候选 8335 行 | ~+44 MB | 全量重建 |

关键斜率：小提交下 A 是 O(N) 每提交；B 是 O(写集) 每提交、与 N 无关；
C 每提交与 N 无关但与**历史版本数**相关，置换越密集候选越膨胀。

### 端到端（真实引擎方向 A，含 fsync，最终 30577 键）

| N | 小提交 p50/p95 (ms) | 大批 500 行 (ms) | 进程重启 (ms) |
| --- | --- | --- | --- |
| 1000 | 5.4 / 8.4 | 25.5 | 111 |
| 8000 | 13.4 / 18.5 | 42.8 | 263 |
| 30000 | 43.8 / 51.6 | 111.3 | 1201 |

小提交 p50 从 5.4→43.8 ms（N 增 30 倍，延迟增约 8 倍，叠加固定 fsync 地板），
重启从 111→1201 ms，均随 N 线性恶化。

## 语义正确性闸门（真实 HTTP 与模拟器双重确认）

同事务值置换 200、释放后复用、删除后复用、多个 null 均 **200 接受**；
两个键抢同一仍被占用的值 **409 conflict 拒绝**。三方向判定完全一致。
